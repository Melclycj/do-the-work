# 跨轮设计判断：构造侧没有结构化的地方放事实

> 2026-08-15。起因是拆分批 R1 与其后一个被撤回的设计轮，一天之内同一缺陷类出现十余次。
> 本文钉住的是**诊断**，不是修法；不裁任何事，不改任何规则。用户 2026-08-15 裁「钉住」。

## 现象

R1 与 ASSERT-OWNER 两轮，三次独立评审共返 15 条 finding + 后续 read 的 3 条。分布：

| 面 | 缺陷数 |
|---|---|
| 被机器守住的（`E2` 冻结 blob · 三条 pre-commit 守卫 · 六条电池 · repo-audit · blob 逐一比对 · ledger cap） | **0** |
| 只有散文的（成员集规模 · `E9` 腿数 · 新仓套件红的成因 · 扫类结果 · 守卫是否可用 · revision 标签） | **全部** |

守卫在其中一次主动拦下 executor（把已删路径写进新增行），改对才放行。

## 三次尝试与结果

1. `HD-41`（2026-08-14）为这个类立条，停在决策簿、指令层零承载 → 次日 R1 出六个实例。
2. 设计轮 ASSERT-OWNER 把它写进指令层（`E3` +11 行 · `E7` +3 · `E13` +15 · `E10` 编号 +10，
   冷读 204→241 行）→ **装的过程中又出七个实例**，其中三个就在回答那些 finding 的 commit 里；
   `E13` 的立论句本身无命令可产出 → FULL `CHANGES_REQUIRED` → 用户裁撤，指令层回 204 行。
3. 拿掉表面：新仓 README 的状态段换成命令表、manifest 由「断言 + 计数」换成「规则 + 名单 +
   一条可跑的命令」→ 这两处不再有可出错的槽位。

三次里只有第三次留下了不依赖记忆的效果。

## 诊断（用户 2026-08-15 提出的三点推出）

**构造侧没有任何结构化的地方可以放事实，于是每个事实都变成散文；而散文是唯一没有被检查的东西。**

三条支撑，各自可复现：

1. **控制面不对称。** 产品 run 一个 `control/` 目录 31 个文件、全部 schema 绑定（仓内 15 个
   schema）；构造批只有一份**自由文本** plan + commit 正文 + 评审记录，schema 0。
   **改规则的那一侧，控制面比跑规则的那一侧弱一个数量级。**
2. **commit 正文被要求同时干四件事。** `E3:50` 把命令输出往里放（"output kept in the commit
   body or the round journal"），`E8:66` 又限制它是一段密实的段落；构造批没有
   `user-decision-*.json`，用户裁决也只能进去；`E11` 的偏差照记同样进去。四个职能，一段话的
   空间。实测本 session 20 个 commit 正文平均 35 行、最长 61。
3. **plan 是这个 harness 里唯一没有形状的产物。** run 有 `run-v2` 模板、裁决有抬头定义的条目
   格式、commit 有 `E8`、评审记录有 review contract、run 的决定有 `user-decision.schema.json`；
   `.goals/plans/` 二十余份 plan，**无 template**。而 plan 是最先写的、是用户真正会读的三样
   之一、也是计数与枚举的发源地。

## 为什么"加规则"对它无效

规则改的是「怎么把散文写对」。而这些东西——成员集、腿数、扫类范围、用户的裁决——**本来就不该
是散文**。给一个没有结构化归宿的事实加一条"要写准"的规则，是在错误的层上施力；两侧各有一份
同规则的复述（`E3` 与 `EXECUTION.md` 第 5 条）也证明这个病不分构造侧产品侧。
