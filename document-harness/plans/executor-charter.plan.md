## The problem

Nothing hands an executor its charter. Three facts, each checked at `f084db4`:

1. `dtw dispatch` has exactly three modes — `--subject` (product-run review), `--range`
   (construction-round review), `--read` (layer read). **All three are review-side.**
2. `ORCHESTRATION.md` says so in as many words: *"its three modes are review-side by
   construction, and none of them dispatches an executor. … Who puts an executor's charter in
   front of an executor is not answered here, and no rule in this layer answers it either."*
3. The same file has the orchestrator *"deliver the round's instruction and subject, and stop
   there."*

So a cold executor session holds an instruction and a subject, and no way to learn that
`EXECUTION.md` exists. The gap is filled today by `EXECUTION.md`'s own *Instruction authoring
rules*, which require standing run-conduct discipline to appear **by reference, in the Context
section only** — i.e. every instruction hand-copies the pointer. The reviewer, by contrast,
gets that pointer generated by the CLI, identically every time.

That asymmetry is what this round removes. `dispatch.py` is already role-aware — its own
comment records a real incident (*"Cite the reviewer's OWN instruction, never the other side's
… Two charters, one module"*), so a third role is an extension of an existing mechanism, not
new machinery, and `E6`'s objection does not reach it.

## What it buys, and what it does not

**Buys.** The executor gets a machine-generated charter. The Context pointer loses its reason
to exist, so the authoring rule that mandates it can be deleted along with every instruction's
hand-copied restatement. Context then carries background only — which converts a semantic
judgement (*is this a legitimate reference to standing discipline, or a demand invented here?*)
into a bright line (*anything demand-shaped in Context is a defect*). That is the structural
win: it is the first time `form_conformance`'s `FORM-NORMATIVE-IN-CONTEXT` intent becomes
reachable, having never once fired across eight closed runs. The construction-side executor —
which has the same gap and no delivery path at all — is covered by the same mode, answering the
first of the two questions the `ORCHESTRATOR-CHARTER` round left open. And one drift surface
goes: N instructions hand-copying one sentence become one CLI constant.

**Does not buy.** It does not detect an invented demand — that stays a reviewer's judgement; the
round only makes such demands conspicuous. It does not settle whether the harness may keep using
product runs as its own samples (open question below). It does not reach the eight closed runs.

## The four user rulings of 2026-08-22 (this file is their carrier until the round records them)

1. **Product-side executor mode emits three things and nothing more**: the run id, the
   instruction's path and revision, and the charter pointer. No enumeration of what to check —
   `dispatch.py`'s docstring already refuses that shape for reviewers (*"once such a section
   enumerates what to check it is a shadow WorkSpec, ex post and approved by nobody"*), and the
   executor mode inherits the refusal. Note the timing that makes this the only honest option:
   the executor is dispatched at the start, when the run directory holds a frozen
   `instruction.md` and little else — the WorkSpec is authored by the executor afterwards
   (`HD-35`).
2. **Construction-side mode emits one sentence** — the charter pointer, deriving nothing. A
   construction round has no control plane to derive from (its range is *"the one thing no
   control plane records"*), and feeding the round name and boundary in by hand would reproduce
   exactly what the module exists to abolish.
3. **Queue head: this round, ahead of the re-rooting item's remaining ten resolution points.**
   Measured basis for the reordering: those ten do not bite today — `cli.py`'s six default to
   the current directory, and the six template scripts' `parents[3]` default resolves to the
   caller root correctly for the caller's layout, verified at `f084db4`. This round bites once
   per new instruction, and the first new instruction is imminent.
4. **The `L-1` scope question is already settled** and is `HD-52`: the START-card rendering
   ruling is general, not enumerated-only. Rider `startcard-form` carries the carrier fix; if
   this round touches the SIMP-C4 bullet anyway, it can redeem that row in the same batch.

## Open question — routed to the user under `R5`, unanswered

**May the harness keep using product runs as samples for its own design questions?** Two
obligations of that shape are on the books:

- **Open-ended.** `CONSTRUCTION-LEDGER.md`'s conversation-only list: *"自 Phase E 起每个真 run 的
  review/closeout 记一行两 map 分类对照 … 改判条件：分歧恒零或恒 paragraph 侧对 → 议 (c) 段落诞生
  义务，恒 unit 侧对 → 议 classification 列去留，两侧各有贡献 → 转常设"*. Three branches, one of
  which makes it permanent — and **no moment is named at which anyone reads the collected data**,
  so the default behaviour is to collect for ever.
- **One-shot, and the next run pays it.** The 保障面二期复盘 pointer (d): the next product run
  measures the new audit-cadence baseline first.

The answer changes this round's shape: if the sampling obligation stands it is standing
discipline and belongs in whatever the new charter points at; if it is retired, one fewer thing
for Context to have ever carried. Three options were put to the user — name a reading moment,
retire it now, or leave it untouched (the default, which is that it continues indefinitely).
