## 3. M2 —— 什么绑住了「脚本必须在 run 目录里」

### 3.1 已知那条成本，读代码复现后**比 §5.2 写的窄**

记录层 §5.2 记的是：*`command_exit` 的 `subject_tree: candidate_commit` 要求脚本存在于物化的候选
树里，所以「只引用」不是无代价的*。逐层读下来，要求的**不是 run 目录，是「在候选 commit 里被
提交」**：

- `checks.py:334-338` `_check_command_exit`：声明 `candidate_commit` 时转
  `materialized_candidate(repo_root, candidate_revision)` 并在其中运行。
- `candidate.py:181-185`：`git worktree add --detach <tmp> <revision>` —— 物化的是**整个仓库**
  在该 commit 的树，不是 run 子目录。

**活证据（不是推论）：`p5b-claims` 自己的 check argv 已经在引用 run 目录之外的脚本并且跑通**
（`build_run.py:356-379`）：

```python
RSC = PY + ["ResearchSystem/tooling/rsc.py"]              # run 目录之外
cmd("chk-p2-golden",   PY + ["ResearchSystem/tooling/tests/run_tests.py"])
cmd("chk-repo-audit",  PY + ["Thesis/Work/Tooling/repo-audit.py"])   # ResearchSystem 之外
cmd("chk-pytest",      PY + ["-m","pytest","-q"], cwd="ResearchSystem/tooling")
```

run-v2 README:260-268 把规则写成「Copy it beside the instruction and **freeze both in the base
commit**：the materialized candidate tree must carry the comparator」——**它给的理由被任何已提交
路径满足**，`templates/run-v2/` 同样在物化树里。所以那句里的 *copy* 是惯例，不是该理由的必要条件。

> **这条成本真正的落点是拆分，不是引用。** 只有当被引用的脚本**离开这个仓库**时，
> `subject_tree: candidate_commit` 才真的够不着它。也就是说 §5.2 与硬伤 (b) 的耦合是**成立的**，
> 但账要记在**拆分**头上，不记在「抄件改引用」头上。

### 3.2 真正的硬绑定：`__file__` 相对根 + CONFIG 块

六份模板脚本分两类：

| 脚本 | 绑不绑 run 目录 | 依据 |
|---|---|---|
| `run_evidence_v2.py` · `run_bind_v2.py` · `run_repair.py` | **绑死** | `HERE = Path(__file__).resolve().parent` → `RS_ROOT = HERE.parents[2]` / `REPO = RS_ROOT.parent` / `CONTROL = HERE/"control"` / `EVIDENCE = HERE/"evidence"`。放到 `templates/run-v2/` 就会去找 `templates/run-v2/control` |
| `check_template_instance.py` | 不绑 | `Usage: python check_template_instance.py <run-dir> [<repo-root>]`——run 目录是**参数** |
| `make_paragraph_map.py` | 不绑 | 走 `sys.argv` |
| `compare_blocks.py` | 半绑 | `REPO = Path.cwd()` + `sys.argv`，位置不绑；但带 CONFIG 块 |

第二条绑定与位置无关，是**参数化方式**：README:5-7「Instantiate by copying into
`runs/<run-id>/` and filling each script's CONFIG block」。`RUN_ID` / `BASE` / `CANDIDATE` /
`CANDIDATE_BRANCH` / `REPAIR_ROUND` / `EVIDENCE_COMMIT` / `SOURCE` / `SITES` 是**改文件填进去的**。
共享脚本没法携带 per-run 常量——所以 D1 的工作量真正在这里：**把「改文件填 CONFIG」换成「读
配置 + 传参」**。可行性有现成的落点（run 的 `control/` 本来就全是 JSON），但那是 A2。

## 4. M3 —— CheckResult 不落盘会断什么

### 4.1 先说一条把问题本身推翻的实测：**「重算」这条路对 `command_exit` 不存在**

§5.3 设想的是*从 `chk-*.out.txt` + spec 重算*。读代码：

- `checks.py:384` `evidence = _write_evidence(ctx, check["check_id"], completed.stdout or "")`
  —— 落盘的**只有 stdout**。
- `checks.py:385,391` `allowed = completed.returncode in config["allowed_exit_codes"]` /
  `exit_code=completed.returncode` —— **判据是退出码，而退出码只进 CheckResult JSON**。

反例是决定性的，不是边角：

```
chk-manifest-unchanged.out.txt   0 bytes / 0 lines
check-chk-manifest-unchanged.json → result=PASS  exit_code=0
```

`git diff --exit-code` 成功时 stdout 为空。**一个 0 字节的输出文件里没有任何可重算的东西。**
所以 D2 若答「改重算」，实际得到的不是重算而是**重跑**——重跑要物化候选、要脚本够得着（回到 M2），
是另一个量级的东西，也不再是「从已提交字节确定性重算」。

### 4.2 会断的（硬、机械）

1. **review subject 的完整性检查** —— `review_subject.py:428-445`：committed plan 的
   `check_order` 里每个 `check_id` 都必须在
   `<control_root>/evidence/check-<check_id>.json` 有一份**已提交文件**，缺 → `-CHECK-RESULT-MISSING`。
   该处注释自己写明这是**故意**的：*writing eight results into one aggregate file is reported
   here as eight missing per-result files*——**连合并成一份都算断**，遑论不落盘。
2. **`AssuranceCandidate.check_result_refs`** —— `digestRef`（path + sha256）数组，`p5b-claims`
   有 21 条。不落盘就没有 path 也没有 digest 可钉。（schema 上非 required，但一旦有 local_check
   就会被写。）

### 4.3 不会断的（可从重算/重跑的结果接上）

3. **coverage 的 join** —— `views.py:30-70` `coverage_rows(spec, record, results)`：`results` 是
   **内存序列**，`by_check = {r["check_id"]: r}`，只读 `result["result"]` 一个字段。要的是
   **判据本身**，不是文件。
4. **state 指针** —— `assurance_state.py:81-89` `DIGEST_PROTECTED_FIELDS` =
   {`work_spec_ref`, `start_/repair_/final_decision_ref`, `review_ref`}，**CheckResult 不在其中**；
   `check_results_ref` 只出现在 `review_subject.py:289` 那个 `required=False` 的解析循环里。
   §5.3 把 state 指针列为嫌疑之一，实测它是三个嫌疑里**最松的一个**。

### 4.4 量

`p5b-claims` 的 evidence 目录：`check-*.json` **1,378 行 = evidence 的 44% = 整个 run 的 22%**；
一手输出 `chk-*.out.txt` 仅 481 行（15% / 7.8%）。与 §2 对 `p5b-firewall` 的 19% / 6% 同量级。

## 5. M4 —— 评审记录里有多少是「重推」

方法：取三份记录，**按小节**归三类，规则先写死再套用——
**(A) 结论**（verdict / finding 陈述 / disposition / honesty ceiling 这类「读者要知道的事」）·
**(B) 重推展示**（跑了什么命令、复算出什么数、逐字节比对、血缘追溯、"how I checked it" 表）·
**(C) 骨架**（标题、subject 表、小节头）。

| 记录 | 非空行 | (B) 重推 | (A) 结论 | (C) 骨架 |
|---|---|---|---|---|
| `v3-review-full-8ad8c2f.md`（FULL, p5b-claims） | 179 | 94 · **53%** | 53 · 30% | 32 · 18% |
| `v3-review-verify-275da5b.md`（VERIFY, p5b-claims） | 214 | 125 · **58%** | 60 · 28% | 29 · 14% |
| `v3-review-full-fef3a2e.md`（FULL, p5b-firewall） | 135 | 72 · **53%** | 32 · 24% | 31 · 23% |
| **合计** | **528** | **291 · 55%** | **145 · 27%** | **92 · 17%** |

语料总量（今日重测，§1 当时是 80 文件 / 19,347 行）：

```
v3-review-full-*      35 files   9558 lines  avg 273
v3-checkpoint-read-*  27 files   6300 lines  avg 233
v3-review-verify-*    15 files   4720 lines  avg 314
其他                  18 files   1982 lines
TOTAL                 95 files  22560 lines
```

**答 §5.4：约 55% 是重推，27% 是结论。** §5.4 问的「300+ 行/次」对 VERIFY 成立（均值 314），
FULL 均值 273。

**诚实边界（两条，都影响这个数怎么用）：**
1. 这个分类是**我按上面写死的规则逐节判的，不是机械可复算的**。换个人分，边界会挪几个百分点。
   它足以支撑「重推是大头」，不足以支撑「精确 55%」。
2. **样本偏小**：三份是 189/237/146 行，而语料均值 273/314。抽到的是偏短的。

**这个数对 D3 的意义，要连着计划书 Why 段那条实测一起读**：`HI-REDEEM-5` 量到 FULL 252k tokens /
25.5 分，targeted VERIFY 208k / 23.8 分 = **83%**——主体小三分之二只省 17%。
**砍掉记录里那 55% 的重推，省的是记录的字节，不是评审员的工作**——他照样要重推，只是不再写出来。
`A` 能减少**要读的**，减不掉 `R2` 要求**重新推导的**。所以 D3 实质是在问：*那 55% 是给谁看的、
它不在的时候什么决定会不同*（§3 判据）。

**本 journal 今后用「(记录,文件) 对」**——它答的是「有多少个不同的地方引它」，与「留着有什么用」
这个问题对得上。按该尺：**185**。

> **一条测量本身的怪事，记下来**：`v3-review-full-a7bb1d6.md` 落盘后，上面四份「从未被引」

### 14.3 `f-3` 更正 §12.4 —— 把字符标成了字节，且层已不是九成员

### 14.5 这四条共同的教训，比四个数本身重要

四条里**三条**（`f-1` 的假阳性回流、`f-3` 的成员数、`f-4` 的 B 组）都是**同一个形状**：数量在被
写下之后，被同一轮的后续动作改掉了。`E3` 说的「measure last」不是文风建议——本 journal 一轮之内
就踩了三次。往后本 journal 的任何计数，**要么在轮末重测，要么在数字旁写死测量时的 commit**。
